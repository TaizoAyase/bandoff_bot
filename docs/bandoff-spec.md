# スタジオオフ会 曲・パート管理アプリ 仕様書

## 1. 背景と目的

複数人が楽器を持ち寄ってスタジオに集まるオフ会において、演奏する曲とパート担当を事前に決めるためのWebアプリケーション。

従来はGoogleスプレッドシートや既存のパート募集サービスを利用していたが、以下の課題があった。

- スプレッドシート: 誰のアカウントで管理するかという運用上の面倒さ
- 既存サービス: 一度エントリーすると辞退できない / 登録した楽器を変更できない / 同じ曲の複数パートに入れない

本アプリはこれらを解消し、身内の少人数オフ会に最適化した柔軟な運用を可能にする。

### 想定規模

- Discordサーバー全体: 約50人
- 1回のオフ会参加者: 十数人
- メンバーは毎回入れ替わる
- 地方別に複数のオフ会が並行することがある
- 担当パートは毎回変わりうる(同じになることも多い)

## 2. 設計方針

### 2.1 認証を持たない

Google/Twitter等の外部認証は使わない。制作者が他サービスの認証情報を預かる状況を避けるため。

代わりに以下の3レイヤーでアクセスを制御する。

| レイヤー | 目的 | 手段 |
|---|---|---|
| 到達制御 | 誰がページを開けるか | 推測不能URL + 合言葉 |
| 書き込み制御 | 誰が編集できるか | イベント単位のセッションcookie |
| 本人性 | 誰が自分のエントリーを操作できるか | 端末トークン |

なお、パスワードによる本人性は**善意の集団における事故防止**であり、悪意への防御ではない。「山田」と名乗れば山田になれる。身内オフ会という前提のもとで許容する。

### 2.2 情報をDiscordの外に漏らさない

- `noindex` / `robots.txt` / `X-Robots-Tag: noindex`
- `Referrer-Policy: no-referrer`(外部リンク経由での秘密URL漏洩を防ぐ)
- **OGPを出力しない**。DiscordにURLを貼るとDiscordのプロキシがページを取得して埋め込みを生成するため、イベント名や日時がプレビューに露出するのを防ぐ
- URLのパス・クエリに個人名を含めない
- アクセスログに秘密URLを平文で残さない

### 2.3 Discord Botは「絞り込み」ではなく「発見」のために使う

サーバー50人に対し参加者は十数人なので、Botでギルドメンバーを検証しても絞り込み精度はURL共有と大差ない。

Botの価値は別のところにある。

- 複数イベントが並行するとき、URLの取り違えを防ぐ
- 数週間後に「あのURLどこだっけ」とスクロールを遡らずに済む
- Discordユーザーidが取れるため、本人性の問題と表記ゆれが解消する

したがってBotは必須ではなく、フェーズ2以降の拡張とする。

**フェーズ2で実装したスラッシュコマンドによる発見の仕組み**(詳細は6.7)は次のとおり。

- `/bandoff open` は合言葉を省略し、実行した本人としてそのままイベントに入れる。Discordアカウントを参加者に紐付け、次回からは合言葉なしで入れる
- `/bandoff list` は開けるイベントの一覧をエフェメラル(本人にだけ見える)で返す
- `/bandoff new` はイベント作成ページ(`/new`)を開くリンクを返す。作成者の自動紐付けは行わない(範囲外)
- 使えるのは secret `DISCORD_GUILD_ID` で指定した1サーバーだけ。DM・他サーバーからは使えない
- Discord経由でログインしても**主催者権限は決して付与しない**(4章)。合言葉方式の主催者キーとは独立した仕組みのまま
- コマンドが有効になるのは `DISCORD_PUBLIC_KEY` と `DISCORD_GUILD_ID` の両方が設定されているときだけ(3章)。どちらか一方でもなければInteractionsエンドポイントは404を返し、存在しないものとして扱う

## 3. データモデル

```
Workspace(id, discord_guild_id, name)
 └ Event(id, workspace_id, slug, title, region, starts_at, duration_minutes,
         place, notes, status, join_code, organizer_key_hash,
         organizer_participant_id, discord_enabled, created_at)
     ├ Participant(id, event_id, display_name, instruments,
     │             token_hash, recovery_key_hash, discord_user_id?,
     │             created_at, left_at?)
     ├ DiscordLink(token_hash, event_id, discord_user_id,
     │             display_name_hint, expires_at, used_at?)
     └ Song(id, event_id, title, artist, ref_url, song_key,
            notes, proposed_by, created_at)
         ├ SongScoreUrl(id, song_id, url, label?, sort_order, created_at)
         └ Take(id, song_id, label, order, created_by, created_at)
             └ Slot(id, take_id, instrument, note, order,
                    created_by, created_at)
                 └ Assignment(id, slot_id, participant_id, note, created_at)
```

### 各テーブルの要点

**Workspace** — Discordサーバーに1つ。複数イベントを束ねる単位。`/bandoff list` でのイベント一覧や、将来の演奏履歴の横断参照に使う。

**Event** — 個々のオフ会。`slug` は128bit以上の推測不能文字列。`region` で「東京」「大阪」等を区別する。

`status` は `upcoming` / `closed` の2値。当初は「募集中 / 締切」を分けることを検討したが、**実質的に当日始まるまで募集が続く**ため意味をなさない。開催日時から24時間経過したら自動的に `closed` 扱いとして一覧のデフォルト表示から外す(手動切り替えの忘れを防ぐ)。終了後も閲覧は可能で、主催者による編集も可能。

`organizer_participant_id` — 主催者自身のParticipantへの参照。**主催者は必ず参加者を兼ねる**ため、イベント作成フローで同時に生成する。

`discord_enabled` — このイベントを `/bandoff open`・`/bandoff list` の対象(候補イベント)にするかどうか。主催者が作成フォーム・編集画面のチェックボックスで指定する。新規イベントは初期値オン、既存イベントはマイグレーションでオフになる(6.7)。コマンド自体が無効(`DISCORD_PUBLIC_KEY`・`DISCORD_GUILD_ID` 未設定)でも、この列自体は独立して保持し常に編集できるようにする(後からコマンドを有効にしたときに設定が生きているように)。

**Participant** — イベント単位の参加者。**イベントを跨いだPerson は持たない**。担当パートが毎回変わる以上、名寄せして属性を持ち越す価値が薄いため。

`instruments` は「今日持ち込む楽器」の自己申告(例: `Gt, Ba`)。曲ごとの担当を縛るものではなく、当日の機材の見通しを立てるための情報。「ベースが1本しか来ない」「アンプが足りない」といった事故を防ぐ。

`recovery_key_hash` については 8.1 を参照。

`discord_user_id` — 紐付いたDiscordユーザーのID(未紐付けなら`null`)。1つのイベント内で、**現在参加中**(`left_at is null`)の参加者に対しては同じDiscordアカウントが2人以上紐付かないよう部分ユニークインデックス(`event_id, discord_user_id` に `left_at is null and discord_user_id is not null` の条件を付けたもの)で保証する。参加を取りやめた行(`left_at`あり)は対象外なので、取りやめ後に同じDiscordアカウントで登録し直せる。紐付け・解除の詳細は6.7を参照。**JSONエクスポートにはこの値を含めない**(2.2の「Discordの外に漏らさない」対象そのものではないが、DiscordユーザーIDと参加者を結び付ける情報を外部に出さない方針のため)。

**DiscordLink** — `/bandoff open` 等が発行する、1回限りのイベント参照リンク用トークン。平文のトークンは保存せず、SHA-256ハッシュ(`token_hash`)のみを主キーとして持つ。発行から600秒(10分)で失効し(`expires_at`)、消費すると`used_at`が立って以後は無効になる。発行のたびに期限切れの行を掃除するため、テーブルの行数は常に小さく保たれる。`display_name_hint`は発行時点でのDiscord側の表示名(サーバーニックネーム→グローバル表示名→ユーザー名の優先順位)で、参加者登録時の表示名の初期値に使うだけの一時的な値。

登録時、`display_name` が同一イベント内で**完全一致**する既存参加者がいれば警告を出す。ただし確定は可能(表記ゆれの吸収などは行わない)。

**参加の取りやめ・主催者による削除は物理削除せず `left_at`(取りやめ日時)を立てるだけに留める。** Song の `proposed_by` やTake/Slotの `created_by` がParticipantを参照しているため、行ごと消すとその参照が壊れる。一覧表示・表示名の重複警告・端末トークンの再紐付け・復帰キーによる復旧は `left_at is null` の参加者だけを対象とし、JSONエクスポートのみ取りやめ済みも `left_at` 付きで含める。取りやめ・削除と同時に、その参加者の全エントリー(Assignment)もまとめて削除する。**主催者自身のParticipant(`organizer_participant_id` が指す行)は、本人による取りやめも他者による削除も対象外とする。**

**Song** — 演奏する曲。曲順は持たない。当日その場で決めるため、登録順(`created_at`)で表示すれば十分。

**SongScoreUrl** — 曲に紐づく譜面のURL。1曲に複数登録できる(上限10件)。登録順(`sort_order`)と、任意の名前(`label`、20文字以内)を持つ。名前は必須ではなく、付けなければ `null`(空文字は保存しない)。曲カードでの見え方は5章。同じURLでも名前が違えば別の行として扱い、`(url, label)` の組が完全に一致するものだけを重複として落とす。`Song.ref_url`(参考音源・動画、単一・任意)とは別項目で、両者は並存する。曲の編集は全件を送り直す方式で、送られなかった既存の行は削除される(差分更新はしない)。JSONエクスポート(9.3)の `scoreUrls` は `{"url": …, "label": …}` の配列で出す(名前を持たなかった頃はURLの文字列配列だった)。

**Take** — 同じ曲を複数回演奏する場合の単位。「1回目はGt、2回目はBa」という持ち替えを表現するために必要。デフォルトはTake1のみ。

**Slot** — パートの「枠」。`instrument` は `Gt` `Ba` `Dr` `Vo` `Key` など。同じinstrumentが複数ある場合は表示時に `Gt1` `Gt2` と自動採番する。`note` は「リード」「コーラス兼任」等の自由記述。

**Assignment** — 誰がその枠に入るか。楽器はSlot側が持つので、Assignmentは紐付けとメモのみ。

### 設計上の要点

**SlotとAssignmentを分ける。** 曲を登録した人が枠を切り、参加者がそこに入る。これにより空き枠が可視化され、「Ba募集中」が一目でわかる。

**`(slot_id, participant_id)` にのみuniqueを張る。** `(song_id, participant_id)` には張らない。これにより同じ曲でGtとコーラスを兼ねることができる。

**楽器の変更は、別のSlotに移ることで行う。** 従来サービスの「登録した楽器を変えられない」という制約は、Assignmentを削除して別Slotに作り直すだけで解消される。

**辞退はAssignmentの削除であり、Slotは残る。** 辞退しても枠は空いた状態で残るので、他の人が拾える。辞退と枠削除は完全に別操作。

## 4. 権限

| 操作 | 参加者 | 主催者 |
|---|---|---|
| 曲の登録 | ○ | ○ |
| 曲の削除 | 自分が登録した曲かつ誰もエントリーしていない場合のみ | ○ |
| 曲情報の編集 | ○ | ○ |
| Takeの追加 | ○(全曲) | ○ |
| Takeの削除 | 中の全Slotが空の場合のみ | ○ |
| 枠(Slot)の追加 | ○(全曲) | ○ |
| 枠の削除 | 空の枠のみ(全曲) | ○(埋まっていても) |
| 自分のエントリー | 追加・辞退・移動すべて自由 | ○ |
| 他人のエントリー | × | ○ |
| 他人のエントリーの一括辞退 | × | ○ |
| 自分の参加を取りやめる | ○(主催者自身は不可) | ×(主催者自身の分は取りやめ不可) |
| 他人を参加者から外す | × | ○(主催者自身は対象外) |
| イベント情報の編集 | × | ○ |

### 判定の原則

枠の削除可否は「誰が作ったか」ではなく **「空かどうか」** だけで判定する。枠の追加を全曲に開放する以上、削除も同じ基準にするのが一貫している。

- 他人が入っている枠は削除できない(空でないため)
- 自分が入っている枠も、まず辞退してから削除する
- 空枠が誤って消されても、また追加すれば済む。`created_by` を記録しておけば経緯も追える

主催者が埋まった枠を削除する場合は、確認ダイアログに中の人の名前を出す(例:「Gt2(山田さん)を削除します」)。

曲情報の編集と削除は、あえて基準を分けている。

- 編集は登録者に限らず参加者なら誰でもできる。誰かが練習中に気づいたキーや譜面URLの誤りをその場で直せた方が実際の運用に合っている
- 編集内容は通知に「〇〇さんが変更しました」と出るため、誰が何を変えたかは後から追える
- 一方で削除は取り返しがつかない(曲に紐づくTake・Slot・エントリーがまとめて消える)ため、登録者本人と主催者だけに限定する

### 主催者の判定

- イベント作成時にサーバーが発行する主催者キー。入力すると主催者フラグをcookieに保持する。これが唯一の判定経路

主催者キーを共有すれば複数人が主催者として振る舞えるので、当日に主催者がスマホを見ていない場合でも詰まらない。

**Discord経由(`/bandoff open` でのリンク消費)では主催者権限を決して付与しない。** cookieの主催者フラグは、Discordリンクを消費する前の値をそのまま保つ(付けもしないし消しもしない)。これは、たとえ紐付け先のDiscordアカウントの持ち主が当該イベントの主催者自身であっても同様で、主催者自身がDiscord経由で入っても主催者画面は開けない(通常どおり合言葉方式で主催者キーを入れ直す必要がある)。Discordのユーザーidだけを根拠に強い権限を渡さない、という判断による。

## 5. 画面構成

### 曲一覧(メイン画面)

先頭にイベント情報を出す。イベント名・開催日時と長さ・場所の3点。
当日スタジオで「何時から何時まで、どこで」を確認する用途が主なので、
地域は場所と重複しがちなため出さない。

この情報は合言葉を通した後にしか見えない(`requireViewer`)。URLだけが
漏れた場合に中身を渡さないための境界なので、認証前のレスポンスに
イベント名が含まれないことはテストで固定する。

曲カードを縦に並べる。1曲1カードで、中にSlotが横並び。埋まっている枠は参加者名、空き枠は「+ 参加」ボタン。譜面URLが登録されていればリンクを出す。名前が付いていればその名前だけを、付いていなければ「譜面1」「譜面2」…と番号を表示名にする。番号は名前付きの行も含めた全体の通し番号なので、名前の有無が混在すると「譜面1 / ギター / 譜面3」のように番号が飛ぶ(`rel="noreferrer"`を必ず付け、秘密slugを含むページURLがReferer経由で外部サイトに渡らないようにする)。名前は登録者が自由に決められ、曲情報は参加登録した人なら誰でも編集できる(4章の権限表)ため、他人が登録した行の名前も含めてリンクの文言はリンク先の内容を保証しないが、招待制のイベント内に閉じた話であり`rel="noreferrer"`によって秘密slugの漏洩は防がれているので、この性質は受け入れる。

曲数が増えても破綻せず、スマホでも成立する。スタジオで当日スマホから見ることを考えると実質これ一択。人×曲のマトリクス表示はPCでしか成立しないので、必要になったら補助的に追加する。

### Takeの見せ方

**Takeが1つのときはTakeの存在自体を隠す。** 曲カードを開くとSlotが並んでいるだけで、下に「2回目を追加」の控えめなボタンがある。2つ以上になって初めて「1回目 / 2回目」の見出しが現れる。

Takeを使わない大多数のユーザーに複雑さを見せないための措置。

Take追加時は **Take1の枠構成をコピーする**(中の人は空)のをデフォルトにする。「同じ曲を違う編成でもう一回」が動機なので、枠構成は同じであることがほとんど。

### 自分のエントリー一覧

「自分が何曲で何を弾くか」を確認する画面。当日最も使う機能なので独立して用意する。

### 参加者一覧

名前と持ち込み楽器の一覧。当日の機材確認に使う。主催者には各行に「参加者から外す」ボタンが出る(主催者自身の行を除く)。取りやめ・削除済みの参加者はこの一覧から消える。

### 主催者画面

イベント情報の編集、ステータス変更、他人のエントリーの操作、参加者の削除。イベント編集フォームには「Discordの/bandoffコマンドから開けるようにする」チェックボックスがあり、現在の`discord_enabled`の値を反映して保存する(コマンドが無効でも常に表示・編集できる)。

### Discordアカウントの紐付け(曲一覧・設定画面)

`/bandoff open` で発行されたリンクを消費した直後、曲一覧の先頭に確認バナーが出ることがある(6.7)。

- 参加者として端末に紐付いているが、そのDiscordアカウントとはまだ紐付いていない場合:「このDiscordアカウントを「{参加者の表示名}」と紐付けますか? 紐付けると、次回からDiscordの/bandoff openでそのまま入れます」+ [紐付ける] [今はしない]。表示名は参加者側の表示名であり、Discord側のニックネーム等は出さない
- 参加者としてまだ登録していない場合:「Discordから開きました。参加登録すると、次回から/bandoff openでそのまま入れます」+ [参加登録する] / 「登録済みの人は[引き継ぎコードで入る]」

設定画面には「Discordアカウント」カードがある。

- 紐付け済み: 「Discordアカウントと紐付いています」+ [紐付けを解除する](確認ダイアログ付き)
- 未紐付けで、かつそのイベントが`discord_enabled`: 「Discordの/bandoff openから開くと紐付けられます」というヒントのみ
- それ以外(未紐付けで`discord_enabled`でない): 何も出さない

いずれの画面でも、DiscordのユーザーID・表示名は一切出さない(そもそも表示名は保存していない)。

## 6. 利用動線

フェーズ1(合言葉方式)を前提とする。

### 6.1 主催者:イベント作成

1. `/new` を開く(誰でもアクセス可。他人のイベントは覗けないため)
2. イベント情報を入力(タイトル、地域、日時、長さ、場所、備考)。日時は日付のカレンダー入力と15分刻み96択の時刻選択に分ける(`step` 付きの `datetime-local` は任意の時刻を打ててしまい、送信するまで弾かれないため)。長さは30分〜8時間の選択式(未設定も可)
3. **同じフォームで自分の表示名と持ち込み楽器も入力**する。主催者は必ず参加者を兼ねるため、ここで Participant を同時に生成し `organizer_participant_id` に紐付ける
4. 合言葉(参加者用)を設定。主催者キー(編集・代理操作用)は作成時にサーバーが発行する
5. 作成 → slugが生成され `/e/{slug}/` へリダイレクト。主催者cookieが立ち、復帰キーが表示される
6. 「Discordに貼る文面」(URLと合言葉をまとめたテキスト)をコピーボタンで取得し、Discordに投稿

### 6.2 参加者:初回アクセス

1. DiscordのURLをタップ
2. 合言葉入力画面。**イベント名も表示しない**(URLだけ漏れた場合の情報露出を防ぐため)
3. 合言葉を入力 → イベントスコープのcookieが立つ
4. 曲一覧が見える。**この時点では参加者登録は不要**。閲覧のハードルを下げる
5. 「+ 参加」を押すと参加者登録モーダル(表示名、持ち込み楽器)
6. 登録完了 → 復帰キーが表示され「メモしました」にチェック。トークンがlocalStorageに保存される
7. **そのまま 5 で押した枠へのエントリーが確定する**。登録で終わらせず、元の操作まで完走させる

### 6.3 曲の登録

1. 「曲を追加」を押す
2. 曲情報を入力(タイトル、アーティスト、参考URL、譜面URL(複数可、最大10件)、キー、備考)。譜面URLは1行ごとにURLと名前(任意・20文字以内)を入力する。名前だけを入れてURLを空にした行はエラーにする(どちらも空の行は黙って無視する)
3. パート構成を決める。**Gt / Gt / Ba / Dr / Vo が入った状態を初期値**とし、増減させる。ゼロから組ませない
4. 登録すると内部的にTake1が生成される(UI上「Take」の語は出さない)
5. 自分が弾く枠に入る。**提案者を自動でエントリーさせない**(「Voは誰かやってほしい」があるため)

### 6.4 2回目以降のアクセス

cookieとlocalStorageが生きていれば、URLを開くだけで「自分」として認識された状態の曲一覧が出る。合言葉も名前入力も不要。

cookieが切れていれば合言葉から。localStorageが消えていれば復帰キーで自分に紐付け直す(8.1)。

### 6.5 変更・辞退

| やりたいこと | 操作 |
|---|---|
| 楽器を変える | 現在の枠で「辞退」→ 別の枠で「+ 参加」。曲カード内で完結する |
| 辞退する | 「辞退」を押す。枠は空のまま残り、他の人が拾える |
| 枠を足す | 誰でも、どの曲にでも追加できる |
| 空き枠を消す | 誰でも可。埋まっている枠は不可 |
| 同じ曲をもう一度 | 曲カード下部の「2回目を追加」。Take1と同じ枠構成が空で複製され、ここで初めて「1回目 / 2回目」の見出しが現れる |
| 参加を取りやめる | 設定画面の「参加を取りやめる」。確認ダイアログに残っている全エントリー(曲名・パート)を列挙し、まとめて辞退させたうえで参加自体を取りやめる(主催者自身は不可) |
| 参加者を外す(主催者) | 参加者一覧の「参加者から外す」。取りやめと同様、対象者の全エントリーをまとめて辞退させる。公開チャンネルでの摩擦を避けるためDiscordには通知しない(主催者自身は対象外) |

### 6.6 当日

1. スマホでURLを開く
2. 「自分のエントリー」タブで担当を確認(当日の主役はこの画面)
3. 参加者一覧で機材を確認
4. 開催日時から24時間経過で自動的に一覧のデフォルト表示から外れる

### 6.7 Discordから参加する(`/bandoff open`)

合言葉方式(6.1〜6.6)とは別に、Discordのスラッシュコマンドから合言葉なしで入る経路。コマンドが有効(`DISCORD_PUBLIC_KEY`・`DISCORD_GUILD_ID`が両方設定されている)かつ対象イベントが`discord_enabled`のときだけ使える。候補になるイベントは、作成時から開始+24時間までのもの(締切済みも含む。既存の`isPast24h`が偽であることと同値)。

```
[Discord] /bandoff open event:(候補から選ぶ)
   ↓ POST /discord/interactions(署名検証)
[Worker] 1回限りのトークンを発行し、DBにハッシュだけ保存
   ↓ 本人にだけ見える応答: 「開く」リンクボタン → https://{ホスト}/e/{slug}/discord#{token}
[ブラウザ] リンクを開く(トークンはURLのフラグメントなのでサーバーのアクセスログに残らない)
   ↓ JavaScriptがフラグメントを読み、URLからすぐ消してからfetchでPOSTする
[Worker] トークンを消費し、cookieを張って曲一覧へ
```

- トークンは発行から10分間・1回だけ有効。他の人に渡さないよう応答メッセージに明記する
- 紐付け先の決め方(消費した瞬間の状態で3通りに分岐):
  - A. そのDiscordアカウントが、このイベントの参加中の参加者に**既に紐付いている** → その参加者として入る(紐付け確認は出ない)
  - B. Aでなく、その端末が**未紐付けの参加者としてログイン中** → そのままその参加者として入り、確認バナー(5章)を出す
  - C. それ以外(未ログイン、または既に別のDiscordアカウントに紐付き済みの参加者としてログイン中) → 未登録の状態にして、確認バナー(5章)を出す
  - どの場合も、**主催者フラグ(cookie)は元の値をそのまま保つ**(4章「主催者の判定」)。Discord経由での付与・剥奪は一切行わない
- `/bandoff list` は候補イベントの一覧をエフェメラルで返す。既にそのDiscordアカウントで参加登録済みのイベントには「(参加中)」が付く。各イベントに「開く」ボタンがあり、押すと`/bandoff open`と同じ処理でリンクが発行される
- `/bandoff new` はイベント作成ページ(`/new`)へのリンクを返すだけで、トークンは発行しない。作成者とDiscordアカウントの紐付けは行わない(範囲外)
- 自動紐付け: 参加者登録(`POST /participants`)・端末の引き継ぎ(`POST /recover`)が成功した際、直前にDiscordリンクを消費していれば(未紐付けかつ、そのイベントで同じDiscordアカウントが他の参加者に紐付いていない場合に限り)その場で自動的に紐付ける。既に他の参加者に紐付き済みなら、上書きせず紐付けなしで処理を成功させる
- 紐付けはいつでも設定画面から解除できる(5章)。解除してもcookieのログイン状態は変わらない

**cookieでの受け渡し(`d`=紐付け待ちのDiscordユーザーID、`dn`=登録時の表示名の初期値)**: リンクを消費してからB/Cの状態で紐付け確認バナーを閉じる(または紐付ける)までの間、cookieにこの2つを一時的に保持する。以下の操作をまたいでも消えない: 端末トークンの再結合(`/session/rebind`)、主催者ログイン・ログアウト。一方、以下の操作では紐付け待ちを消す(次回以降に持ち越さない): 合言葉での入場(`/join`)、この端末の紐付け解除(`/settings/unbind`)、参加の取りやめ、新規イベント作成(`/new`)、そして紐付け・引き継ぎが成立した(または断った)時点。

## 7. 挙動の詳細

### 同一人物の重複エントリー

同じTake内で1人が複数のSlotに入ることは **警告は出すが禁止しない**。

- 同じTakeでGtとBaを同時 → 物理的に不可能。警告対象
- 同じTakeでGtとコーラス → 十分ありうる。警告は出るが確定できる
- Take1でGt、Take2でBa → 完全に正当。警告不要

判定をアプリ側で厳密にやるのは無理なので、人間に判断させる。

### 楽器選択の初期値

エントリー時、**そのイベント内で自分が直近に選んだ楽器**をデフォルトにする。Gt担当の人は毎回そのまま確定でき、今回だけBaをやる曲で変更すればいい。

イベントを跨いだ記憶は持たない。イベント内だけで十分効く。

### 変更の通知

エントリーの追加・辞退に加えて、イベントの作成・編集、曲の追加・編集、Take(2回目以降)・枠の追加、参加者登録もDiscord Botでチャンネルに流す(例:「〇〇さんが△△のGt2に入りました」「〇〇さんが△△のBaを辞退しました」)。

辞退のハードルを下げつつ、主催者・参加者が状況を把握できるようにするため。

- 通知先はイベントごとではなく**Worker全体で1つのBot・1チャンネル**(Bot TokenとチャンネルIDをいずれもsecretとして保持)とする。全イベントの通知が同じ1チャンネルに流れるため、本文の先頭にイベント名を前置して区別する。Bot TokenとチャンネルIDの両方が揃わなければ通知は行わない(完全なno-op)。
- 秘密URL・合言葉・引き継ぎコードなど「Discordの外に漏らさない」対象(2.2)の値は本文に含めない。**新しいイベントの作成通知にもこの方針が及び**、URL・合言葉・主催者キー・引き継ぎコードは本文にもURLにも含めない(イベント名・主催者表示名・地域・日時・場所のみを載せる)。
- ユーザーが自由に入力できる値(表示名・曲名・アーティスト名・楽器名など)からのメンション発火を防ぐため、送信時は`allowed_mentions`を空にする。
- 場所・曲名などのユーザー入力にURLが含まれていても、DiscordがリンクプレビューのためにそのURLを取得しない(2.2でOGPを出さないのと同じ理由)よう、送信時に`SUPPRESS_EMBEDS`(`flags: 4`)を指定する。

通知の対象:

- エントリーの追加・辞退(従来どおり): 「〇〇さんが△△のGt2に入りました」「〇〇さんが△△のBaを辞退しました」
- イベントの新規作成(`POST /new`): 「〇〇さんが新しいオフ会を作成しました」+ 地域・日時・場所。作成したイベントが`discord_enabled`、かつコマンドが有効(`DISCORD_PUBLIC_KEY`・`DISCORD_GUILD_ID`が両方設定されている)なら、末尾に「Discordの`/bandoff open`で開けます」の1行を足す(この行にもURL・合言葉は含めない)
- イベント情報の編集(主催者画面): 「イベント情報が変更されました」+ 変わった項目だけを変更前→変更後で列挙(募集状況は主催者画面の表示に合わせたラベルにする。備考は値を出さず「変更しました」とだけ表示)。何も変わっていなければ通知しない
- 曲の追加: 「〇〇さんが「曲名」を追加しました」+ アーティスト(空なら省略)・パート
- 曲情報の編集: 「〇〇さんが「曲名(変更前)」の曲情報を変更しました」+ 変わった項目だけを列挙(参考URL・譜面URL・備考は値を出さず「変更しました」とだけ表示)。譜面URLは並び順と各行の名前を含めて前後を比較し、集合が同じでも並び替えれば変更ありとする。URLはそのままで名前だけを変えた場合も「譜面URLを変更しました」として通知する(名前も値は出さない)。何も変わっていなければ通知しない
- 2回目以降のTakeの追加: 「〇〇さんが「曲名」のn回目を追加しました」
- 枠の追加: 「〇〇さんが「曲名」に◯◯の枠を追加しました」+ メモ(あれば)
- 参加者登録(枠を選ばない、または枠が無効・先を越された場合): 「〇〇さんが参加登録しました」
- 参加者登録とエントリーの成功が同時に起きた場合: 「〇〇さんが参加登録し、「曲名」の◯◯に入りました」の1通にまとめる(登録通知とエントリー通知を分けて2通送らない)
- 参加の取りやめ(自分から): 「〇〇さんが参加を取りやめました」+ 辞退した全エントリー(曲名・パート)の列挙(あれば)。**主催者による参加者の削除は通知しない**(公開チャンネルでの摩擦を避けるため)

新しいイベントの作成通知には荒らし対策として回数の上限がある。直近1時間にサイト全体で作られたイベントが3件を超えたら、4件目以降は通知だけを省く(イベントの作成自体・welcomeページの表示は常に成功する)。この上限はDBスキーマの変更なしで、既存の作成日時から件数を数えて判定する。

## 8. セキュリティ

- 合言葉・主催者キー・復帰キーは試行回数のレート制限を必須とする
- パスワードはハッシュ化して保存
- 参加者トークンはサーバー発行のランダム値。ハッシュを保存し、平文はブラウザのlocalStorageにのみ置く
- イベント単位でcookieのスコープを切る。**東京回に入れることが大阪回に入れることを意味しない**

### 8.1 復帰キー(ユーザー入力パスワードを採らない理由)

別端末からのアクセスやlocalStorage喪失時の復旧手段として、当初は「任意の編集パスワード」を検討したが、**採用しない**。

パスワードの使い回しは非常に一般的であり、ユーザーに自由入力させると**他サービスで使っているパスワードが本アプリのDBに入る**。ハッシュ化していても、預かるべきでない情報を預かることになる。

代わりに、参加者登録時にサーバーが**復帰キー**を発行する。

- 形式は誤読しにくい文字セット(Base32から `I` `O` `0` `1` を除去)で `K7QM-3XPT-9RVN` のような区切り付き12文字程度。エントロピーは60〜64bit あれば十分
- サーバーはハッシュのみ保存し、**平文は再生成しない**
- 通常はlocalStorageのトークンで動作するため、出番は端末変更時のみ

UI上は「パスワード」と呼ばない。その語を見ると自分のパスワードを入力しようとする人が出るため、**「復帰キー」「引き継ぎコード」**と表記する。

**メモし忘れ対策**(必ず一定数が「後で」と思って閉じるため):

- 登録完了時に「メモしました」のチェックを1つ挟む
- 復帰キーは localStorage にも保持し、設定画面からいつでも再表示できるようにする(端末が生きているうちなら救済できる)
- 最終手段として主催者による代理操作を残す

再表示可能にするのは厳密なセキュリティ設計としては緩いが、身内オフ会という前提では**キーを失うリスクの方が大きい**と判断する。

主催者キーも同じ理由でサーバー発行とする。平文は端末のlocalStorageにのみ置き、主催者画面で再表示できる。

## 9. 技術構成

Cloudflare Workers + D1 を想定。

- 無料枠で収まる規模(十数人 / 月数回)
- サーバー管理が不要
- フェーズ2のDiscord Interactionsも同じWorkerで受けられる
- アプリとDBが同じ事業者内で完結する

### 9.1 デプロイ先とデータの所在

**コード** — Cloudflareのエッジネットワーク上で動く。特定のサーバーを借りるのではなく、リクエスト時に関数が起動して応答する。デプロイは `wrangler deploy` を手元から叩くか、GitHubへのpushからGitHub Actions経由で自動化する。静的アセットもWorkerから配信できるので、Pagesと分けず1つのWorkerにまとめる。

**データ** — Cloudflare D1(Cloudflare管理のSQLite)。作成時にロケーションヒントでAPAC(東京/大阪)を指定する。

データ量は1イベントあたり数百行・数十KB程度。年間何十回開催してもストレージは問題にならない。

### 9.2 「Discordの外に漏れない」の正確な意味

この構成では、データは物理的にCloudflareのサーバー上に存在する。厳密にはDiscordの外にある。

実際に守れているのは**不特定多数から見えないこと**であって、ホスティング事業者に預けていないことではない。これはどの構成を選んでも同じで、避けるには自宅サーバーを立てるしかない。

扱う情報が「誰がいつどこのスタジオで何を弾くか」であることを踏まえ、事業者に預けること自体は許容する。ただし日時と場所は個人の行動情報であることは認識しておく。

### 9.3 アカウント問題は完全には解消しない

当初の動機は「誰のGoogleアカウントで管理するか問題」だったが、Cloudflareアカウントも誰かが持つ必要がある。構造としては同じ。

ただし性質は異なる。スプレッドシートではオーナーのアカウントがUIに露出し権限管理もアカウント単位だったが、自作アプリではアカウントは参加者から見えず、デプロイと請求だけの話になる。

一方で bus factor は残る。メンテナンスが止まればデータごと使えなくなる。保険として**イベントデータのJSONエクスポート機能を最初から実装する**。数十行で済み、「スプレッドシートに戻す」経路が確保されているだけで運用上の安心感が違う。

バックアップは `wrangler d1 export` で月1回程度、手元にSQLファイルを落とす。

### 9.4 負荷の見積もりとポーリング設計

負荷のピークは**当日ではなく募集開始の直後**にある。当日は一度見れば済むが、募集開始時は「人気曲のGtが埋まるか」を見るためにタブを開きっぱなしにする動機が働く。

15人が10時間開きっぱなしにした場合、5秒ポーリングでは約108,000リクエストとなり、Workers無料枠(10万/日)を超える。

対策を効果順に並べると:

| 対策 | 効果 | 実装コスト |
|---|---|---|
| 非アクティブタブでのポーリング停止 | 約40分の1に減 | 小 |
| 動的ポーリング間隔(5〜60秒) | さらに数分の1 | 小 |
| ETag / 304 Not Modified | リクエスト数は不変、D1読み取りを削減 | 中 |

**フェーズ1では非アクティブ停止のみを実装する。** これだけで、実際に画面を見ている時間が1人15分程度と仮定すると約2,700リクエストまで落ち、無料枠に対して十分な余裕が生まれる。

実装の要点:

- `visibilitychange` を監視し、hidden でインターバル停止、visible で再開
- **復帰時は即座に1回フェッチしてから**インターバルを再開する。これが抜けるとタブに戻ってから数秒間古い画面が見える
- モバイルSafariでは別アプリ切り替え時に `pagehide` になるケースがあるため、`pagehide` / `pageshow` も拾う
- `beforeunload` は使わない。bfcacheを無効化するため

なお静的アセットの配信はWorkersリクエストとしてカウントされない。課金対象はAPIコールのみ。

**次の対策を足す判断基準**: Cloudflareダッシュボードの日次リクエスト数を確認し、募集開始があった日で1日2万を超えるようなら動的ポーリング間隔を追加する。ETag/304 はD1の読み取り回数が問題になってからでよい。

無料枠に収まらなくなった場合はWorkers有料プラン(月5ドル、1000万リクエスト/月)に移行する。Durable Objectsも使えるようになるため、ポーリングをやめてSSEに移行できる(接続時1回の課金で済むため、この負荷パターンには本来SSEが適している)。

### 9.5 書き込み競合の防止

**これはフェーズ1から必須。** 後から入れるのが難しいため。

募集開始直後には「最後のGt1枠に2人が同時応募」が現実に起こる。「空きを確認 → 挿入」の2ステップにすると、その隙間で競合して二重登録される。

1つのSQL文で完結させる:

```sql
INSERT INTO assignment (id, slot_id, participant_id, created_at)
SELECT ?, ?, ?, ?
WHERE NOT EXISTS (
  SELECT 1 FROM assignment WHERE slot_id = ?
);
```

挿入行数が0なら「先を越されました」を返す。同時に到達しても片方だけが通る。

上記は「1枠1人」を前提とする。1枠に複数人を入れたい場面(コーラス等)が出てきた場合は、Slotに `capacity` を持たせて `COUNT(*) < capacity` で判定する形に拡張する。当面は1枠1人で足りる想定。

### 9.6 検討した他の構成

| 構成 | 費用 | 向いている点 | 懸念 |
|---|---|---|---|
| **Cloudflare Workers + D1** | 無料 | 管理不要、Botも同居、DBが同一事業者内 | SQLiteの制約、Cloudflare依存 |
| Vercel + Turso / Neon | 無料 | Next.js等が素直に動く | 管理先が2つに分かれる |
| Fly.io + SQLite | 月数ドル〜 | 普通のサーバーとして書ける | ボリューム管理、バックアップ自前 |
| VPS + Docker | 月数百円〜 | 完全に自分の管理下、国内 | OS更新・証明書更新などの運用 |
| Supabase | 無料枠あり | Postgres、管理画面が便利 | 非アクティブでプロジェクトが停止 |

なお「バックエンドなしの静的サイト」は選択できない。複数人が同時に書き込む以上、状態を1箇所で持つ必要があるため。

## 10. 開発フェーズ

### フェーズ1: Webのみ

- 推測不能URL + 合言葉によるアクセス
- 参加者名は手入力
- 上記のデータモデル・権限・画面・動線をひととおり実装
- 復帰キーの発行と復旧フロー(8.1)
- 非アクティブタブでのポーリング停止(9.4)
- 条件付きINSERTによる書き込み競合の防止(9.5)
- イベントデータのJSONエクスポート(9.3)

これだけで従来のスプレッドシートより明確に良くなる。**まず1回のオフ会で実際に回してみる**ことを推奨する。パート持ち替えのUIなど、机上で決めきれない部分の答えが出る。

メンバーが毎回入れ替わる集団では、UIの使いやすさが認証の厳密さよりずっと重要。初参加の人が迷わず入れるかどうかが実質的な成否を決める。

### フェーズ2: Discord Bot追加(実装済み)

`/bandoff list`(開催予定イベント一覧をエフェメラルで返す)・`/bandoff open`(専用リンク発行)・`/bandoff new`(作成ページへのリンク)を実装済み。詳細な挙動は6.7、データモデルは3章、画面は5章を参照。

`Participant.discord_user_id` はnullableにしており、手入力方式と共存する。

Discord Developer Portalでのアプリ作成とサーバーへのBot導入は、フェーズ1の通知実装(7章)の時点で済ませてあったため、フェーズ2で新たに必要になったのはPublic Keyの取得(招待スコープには`applications.commands`を既に含めていたため、サーバー管理者への再依頼は不要だった)と、それを使う以下の作業のみだった。

実装した作業:

- Discord Developer PortalでのPublic Keyの取得
- ギルド単位でのスラッシュコマンド登録スクリプト(`scripts/register-discord-commands.mjs`、README「デプロイ」手順7・10)
- Interactionsエンドポイント(Ed25519署名検証をWebCryptoで実装 → PING応答 → コマンド処理)

注意点として、**Discordアプリ内ブラウザ問題**がある。スマホでリンクをタップするとDiscord内蔵ブラウザで開かれ、そこで発行されたcookieは普段使いのブラウザとは別物になる。トークンは10分間・1回だけ有効という短い寿命のままにし、代わりに`/bandoff open`を何度でも叩き直せることを対策とする(「入れなくなったらもう一回コマンド」で復帰できる)。トークンをURLのフラグメントに置く設計(6.7)も、この使い捨てリンクをアプリ内ブラウザで開いたときにアクセスログへ残さないための工夫。

### フェーズ3: 告知の自動化

募集開始のチャンネル投稿、パート充足状況の通知など。

## 11. 意図的に採用しなかったもの

| 項目 | 理由 |
|---|---|
| OAuth (Google/Twitter/Discord) | 認証情報を預かる状況を避ける。今回の規模では過剰 |
| 曲順・セットリスト | 当日その場で決めるため不要 |
| イベントを跨ぐPersonテーブル | 担当パートが毎回変わるため名寄せの価値が薄い |
| 人×曲のマトリクス表示 | PCでしか成立しない。当日はスマホ利用が主 |
| リアルタイム同期(SSE/WebSocket) | 負荷特性としては適するが、Durable Objects(有料)が必要。無料枠で運用したいためポーリング+非アクティブ停止を選択 |
| 動的ポーリング間隔 / ETag | 効果はあるが、まず非アクティブ停止のみで実測してから判断する |
| ユーザー入力の編集パスワード | 他サービスのパスワードを預かる事態を避けるため、サーバー発行の復帰キーに変更(8.1) |
| 「募集中 / 締切」のステータス分離 | 実質的に当日まで募集が続くため意味をなさない |
| 参加者名の表記ゆれ吸収 | 完全一致の警告のみに留める |
| 複数Discordサーバーへの対応 | `discord_guild_id`は1つのWorkspaceに1つだけ。今回の規模では単一サーバー・単一Botで十分 |
| Discord経由での主催者権限の付与 | DiscordのユーザーIDだけを根拠に強い権限を渡さないため。合言葉方式の主催者キーに一本化(4章) |
| `/new`で作成したイベントの作成者の自動紐付け | 作成ページは合言葉より前の公開ページであり、この機能の対象外(6.7) |
| `/bandoff`からの通知チャンネル設定 | 通知チャンネルはWorker全体で1つ(7章)のまま。コマンド経由の変更は範囲外 |
| グローバルコマンド | ギルドコマンドは登録後すぐ反映されるが、グローバルコマンドは反映に時間がかかる。単一サーバー運用のため不要 |
